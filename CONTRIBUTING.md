# Contributing Guidelines – E-Cell RSCOE Website

Welcome to the E-Cell RSCOE Website Development Team! 🚀

These guidelines ensure that everyone can collaborate smoothly, maintain code quality, and avoid conflicts while improving the website.

## 1. Getting Started

- Get access to the official GitHub repository.
- Review the existing website and understand its structure before making changes.
- Read the GitHub Issue assigned to you carefully.
- Ask the Technical Co-Lead if you have any doubts about the requirements.

## 2. Task Assignment and GitHub Issues

- Every feature or improvement must have a corresponding GitHub Issue.
- Work only on the issue assigned to you.
- Read the issue description, requirements, and acceptance criteria before starting.
- Do not work on features already assigned to another contributor.
- If you identify additional improvements, discuss them with the Technical Co-Lead before implementation.

## 3. Branching Rules

- Never make changes directly to the `main` branch.
- Create a separate branch for every assigned issue.
- Use meaningful branch names.

Examples:
- `feature/event-dedicated-pages`
- `feature/hero-animation`
- `fix/navbar-responsive`

Before starting work, ensure your local code is up to date with the latest changes from the main branch.

## 4. Development Guidelines

- Follow the existing project structure and coding conventions.
- Maintain the current website theme, colors, typography, and design consistency.
- Ensure responsive layouts for desktop, tablet, and mobile devices.
- Write clean, readable, and maintainable code.
- Avoid unnecessary dependencies and unrelated modifications.
- Do not delete or overwrite existing features without approval.
- Do not commit environment files such as `.env` or expose API keys, passwords, or other secrets.
- Test your changes locally before submitting them.

## 5. Commit and Push Rules

- Make commits that represent clear, logical changes.
- Use meaningful commit messages.

Examples:
- `feat: add dedicated event pages`
- `fix: improve mobile navigation`
- `style: enhance event card layout`

- Push your changes to your own feature branch.
- Do not force-push or rewrite shared branch history without approval.

## 6. Pull Request (PR) Workflow

Once your feature is implemented and tested:

1. Push your branch to GitHub.
2. Open a Pull Request against the `main` branch.
3. Link the corresponding GitHub Issue in the PR description.

Example:

`Closes #12`

4. Explain what you implemented and which files you changed.
5. Add screenshots for UI-related changes whenever possible.
6. Wait for the Technical Co-Lead to review your PR.
7. Make the requested changes if feedback is provided.
8. Wait for approval before merging.

**Important:** Contributors must not merge their own PRs unless explicitly authorized.

## 7. Code Review and Approval

The Technical Co-Lead will:

- Review the code and implementation.
- Check that the feature meets the issue requirements.
- Verify that existing functionality remains unaffected.
- Request changes when necessary.
- Approve and merge the PR after successful review.

All contributors must address review comments before their changes can be merged.

## 8. Communication and Progress Updates

- Inform the Technical Co-Lead if you encounter blockers.
- Share regular progress updates.
- Discuss major design or architectural changes before implementation.
- Inform the team before modifying shared components.
- Complete tasks within the agreed deadlines.
- If a deadline cannot be met, communicate this in advance.

## 9. Testing Requirements

Before submitting a PR, ensure that:

- The assigned feature works as expected.
- No existing functionality is broken.
- The website works on desktop and mobile devices.
- Navigation and links work correctly.
- No unnecessary files or unrelated changes are included.
- No console errors are introduced by your changes.

## 10. Issue Completion

An issue will be considered complete when:

- All requirements are implemented.
- The changes have been tested.
- The Pull Request has been reviewed and approved.
- The changes have been merged into the main branch.

The Technical Co-Lead will close the issue after verifying completion.

## 11. Golden Rules

1. Never push directly to `main`.
2. Never work on unassigned features without discussion.
3. Never merge your own PR without authorization.
4. Never overwrite another contributor's work.
5. Always communicate before making major changes.
6. Always test before submitting a PR.
7. Always follow the GitHub Issue → Branch → Development → Pull Request → Review → Merge workflow.

## Let's Build Together! 🚀

Every contribution matters. Let's work collaboratively to make the E-Cell RSCOE website more informative, interactive, responsive, and user-friendly.

For questions or technical assistance, contact the Technical Co-Lead.
